### 批 4 — fd 位图保护（两个修复，把 W1 存活从 0/30 抬起来）
- **`reserve_low_fds()`**（`src/core/route/select_stack_route.cpp`）：fd_set 的每个字同时是 waiter 的字段，**字的「值」也会变成 fd 位图**。
  W1 的值是映射页（低字节 `0x00`，只点亮 fd ≥ 8），**W2 的值是 `init_cred` 别名（低 16 位 `0x0930` ⇒ 额外点亮 fd 4 和 fd 5）**，
  而 `open_selected_fds()` 会对每个置位的 fd 做 `dup2` 一个永不就绪的描述符 ⇒ **静默劫持 exploit 自己最早开的管道/socketpair**。
  修复 = 用 `/dev/null` 把 **整个位图范围**（`PSELECT_ROUTE_NFDS = 320` 个槽，实测铺到 `reserved 317 low fds`）占住，并让 `destroy()` 跳过这些槽。
  注释里的关键判据：「The range is the WHOLE bitmap, not just the first 128 descriptors: the waiter words also carry fake_task, fake_lock and the write target.」
- **`raise_pipe_fd()`**（`src/core/session/victim_process.cpp`）：`reserve_low_fds()` 只能占住「之后」分配的 fd；**已经打开的**描述符仍留在位图范围内（位图还覆盖 fd 3..319 中的 131..319，且 fd 0–63 是 `fake_right` 与 `target` 的 OR）。修复 = 子进程的六个管道端逐个 `fcntl(fd, F_DUPFD, PSELECT_ROUTE_NFDS + 96)` 搬到高位。
- **perf ring 扩容**（`src/core/attack/ops.cpp`）：`kPerfDataPages` 32 → **256 页**、候选池 256 → **8192**。原 32 页 ring 只装得下 ~481 个样本（每次采样带 32 个寄存器、~272 B），而请求了 50 万次 `getpid` ⇒ **99.9% 样本被丢弃**，投票数落在 256 上限附近（48–51/256，真指针与噪声无区分度）。**W2 的写目标 `child_task + TASK_CRED_OFF` 就是这个泄漏算出来的 ⇒ 选错就是往随机内核内存写 `init_cred` ⇒ 立即 panic。**
- **perf 三票多数**（`src/core/session/victim_process.cpp`）：从「任意两次连续一致」改为 my2 式三票多数。
  效果实测：从 `236/256`（被截断、无区分度）变为 `7692–7695/8192`（**~94% 一致票**），且三次采样完全一致。

### P0-1 — fork-hold 保活（**已落盘，真机从未执行**）
- 位置：`src/core/support/util.cpp` 的 `hold_reclaim_sockets_until_exit()`（:298 起），调用点在 **`src/core/main.cpp:118`**，紧跟 `run_orchestrated_pipeline()` 之后、`switch (result.code)` 之前。
- 机制（头注释逐字要点）：每个回收描述符关闭时都走同一条内核路径 —— `unix_release_sock → skb_release_data → put_page`，落在**从内核镜像里切出来、从未加过 refcount 的那张页**上。
  这次释放就是「一次跑完的 run」变成 **`BUG: Bad page state`**、并在 `CONFIG_PANIC_ON_OOPS=y` 上**刚刚拿到 root 就重启**的原因。
  `fork()` 让子进程**免费获得整张描述符表自己的引用**，因此父进程退出后仍留一个子进程就能抑制这次释放、且不动页布局。
  **子进程绝不能设 `PR_SET_PDEATHSIG`**——那正是「跟着父进程一起死」从而撤销 hold 的做法。代价 = 每次 run 多一个睡眠进程，下次重启清除。
- 实现细节：`setvbuf` 无关；子进程 `setsid()`（防进程组级 kill 波及）→ `open("/dev/null")` 并 `dup2` 到 0/1/2（让父进程读取端看到 EOF）→ 写 `/proc/self/oom_score_adj = -1000` → `for (;;) pause();`。父进程打 `fork-hold parked pid=%d; reclaim sockets survive this exit`。
- **幂等**：静态 `hold_taken` 保证只 fork 一次；三张页（`current`/`prebuilt`/`quarantine`）都没有 reclaim 时直接 no-op。

### P0-2 — 关掉 W3（**已落盘，真机从未执行**）
- **`app/src/main/assets/kernel_profiles/5.10.149-…-ab9545656.conf`**：`w3_chain_rounds` 3 → **1**、`w3_attempts` 6 → **0**（附 8 行 `#` 注释说明理由）。
- **`src/core/session/backend/cve_2026_43499_backend.cpp`** 的 `w3<M>()`：在 `process_has_seccomp()` 早退之后、`constexpr bool exact_target = M::w3_exact_target;` **之前**插入
  `if (session.profile.w3_attempts() == 0) { pr_warning("W3 disabled by profile (w3_attempts=0); …"); seccomp_ok = 0; return true; }`。
  注释逐字要点：「Skip **before the probe, not inside the write loop, or the probe still fires**. Returns true so the caller **stops the W2/W3 chain** instead of respawning a rooted child to retry a stage we deliberately skipped.」
- **为什么可行且安全**：`w3_attempts()` 走 `GHOSTLOCK_EXEC_U32` 宏**直接读 `values_.execution.name`、不做 `or_default` 兜底** ⇒ 写 0 就是 0（别的执行字段写 0 是「取默认」，只有 `w3_attempts` / `w3_chain_rounds` 例外）。
  Kotlin 侧 `w3_attempts` **零命中**（无任何校验/映射引用），`execution.stages` 段无条件序列化 ⇒ 0 会原样上线。
  **W3 对 uid=0 无用**：`src/core/session/root_child_frontend.cpp:87-95` 的四条分支**全部 `return StageResult::Done`** —— 它只为 KernelSU late-load 开门。

### 关键概率算账
- **`p` ≈ 0.20**（单次 pselect 存活）。
- 一次完整 run 需要 **2 次 pselect**（W1 + W2）⇒ 单轮成功 ≈ `0.2² ≈ 4%` ⇒ **平均约 25 轮才有一次 HIT**。pathA 的 63% 是 8 个样本的运气，**不要当作路径 A 提升存活率的证据**。
- **★ 重要的连锁效应**：`w1<M>()` 开头先查 `attack::check_selinux_off()` —— **一旦本 boot 内 SELinux 已 permissive，就 `pr_success("SELinux already permissive\n")` 直接跳过 W1**（不重写）。
  ⇒ **首次命中之后，同一 boot 内每次 run 只需 1 次 pselect，成功率从 ~4% 跳到 ~20%**。这是「同一 boot 内多跑几轮」策略的核心依据。

## 7. 为什么失败必然重启（硬约束，无法绕过）

- `zcat /proc/config.gz | grep -E 'PANIC_ON_OOPS|PANIC_TIMEOUT'` ⇒ **`CONFIG_PANIC_ON_OOPS=y` / `CONFIG_PANIC_ON_OOPS_VALUE=1` / `CONFIG_PANIC_TIMEOUT=-1`**。
- **提权前关不掉**：`/proc/sys/kernel/panic_on_oops` 非 root **既读不到也写不了**（实测 `Permission denied`）。
  且 W1/W2 的写恒为 **8 字节整字**（Zero 模式 `layout.right = page_base + 0x100`、Credential 模式 `layout.right = init_cred` 别名，且 `payload_write_layout_accepts_page` 要求 `((right >> 16) & 1) != 0`）⇒ **写不出 4 字节的 0，清不掉一个 `int`**。
  NebuSec 的 ionstack writeup 也把 "panic_on_oops disable" 明确列在「已获得任意代码执行**之后**」的手段里。
- 上游对此有明文纪律（`docs/development/design-philosophy.md`）：「**不可观测**：错误发生即重启，栈日志是唯一证词」「**不可迭代**：同一构建可 PASS/panic/PASS」；`docs/development/engineering-standards.md` 的 `KERNEL-PANIC-01`：「单次 panic 不得归因代码」。
- ⚠️ **一个曾经误导过我的错觉，务必纠正**：一度以为「上游从不 panic / main 全程不重启」。**这是删档造成的错觉** ——
  在 `109a0b8`（origin/main 的祖先）时刻 `analysis/device-gates/` 有 **133 个文件**（panic 30 / pass 88 / fail 6），上游用 `064cd1e "docs: drop the stale analysis, gate and PR-note records"` + `c50e3ef "docs: remove docs/analysis from the working tree"` 删掉了 ⇒ `origin/main` HEAD 上 panic 命名文件 = **0**。
  上游真实的成败比（按内核版本分组）：`5.15.189-android13-…-ab14546557` 有 43 份 `.md`，**pass 36 / panic 4 ≈ 9:1**，全部来自同一台设备。
  **对照证据**：`CPP12y` 与 `CPP13b` 是**逐字节相同的 native 二进制**（`66f0a8a3b6450b9c50a02759bcb77162cb3b56af9bb3febcbbac161593184ea6`），`CPP13b` PASS、`CPP12y` panic（`pc : rt_mutex_adjust_prio_chain+0x14b0/0x14c0`）。
  ⇒ **上游也 panic，只是他们的目标机型成功率更高（9:1 vs 我方的 4%）。**

## 8. 为什么 P0-1 / P0-2 至今未被验证（逻辑链，别搞错）

两者都**必须在 W2 成功之后才会执行**：

```
w1<M>()  ──1 次 pselect──►  w2<M>()  ──1 次 pselect──►  child uid = 0
                                                              │
                                                    ┌─────────┴─────────┐
                                              P0-2 早退              否则进 W3
                                          （w3_attempts == 0）       （leaf 探针 4 次 + 2×attempts 次写）
                                                    │
                                        run 结束 ──► main.cpp:118  P0-1 fork-hold
```

`rounds-p01p02` 的 12 轮里 **W2 只进了 1 次（round 5）**，且 round 5 的 W2 pselect **也死在 pselect 里**（日志止于 `consumer gate: waiter parked in syscall 72`）。
⇒ 全批次 grep：**`fork-hold parked` = 0 次、`W3 disabled by profile` = 0 次、`W3-0: leaf dir` = 0 次**。

**所以：机上装的 APK 确实带着两个补丁（字符串已核实），但两个补丁的代码路径一次都没执行过 ⇒ 效果完全未知。**
不要对用户说「P0-1/P0-2 已经修好了重启问题」。

## 12. 结论：下一步该做什么

**不要改代码。** 现在缺的不是补丁，是**样本**：
安装的 APK 已经含有针对「W2 成功后崩在 W3」这一**已观测到的确切失败点**的修复（P0-2 关掉 W3、P0-1 保住退出路径），
但 12 轮里 W2 只成功 1 次且那次也死在 pselect 内 ⇒ 两个补丁未被触发。

**应该做的**：跑一个 **30 轮以上**的批次，盯住三件事 ——
① 是否出现 `W3 disabled by profile`、② 是否出现 `fork-hold parked`、③ **该轮之后设备有没有重启**。
拿到这三条之前，任何「已修好」的说法都是没有证据的。
