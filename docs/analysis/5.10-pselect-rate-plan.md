# 5.10 marble：单次 pselect 生还率 —— 测量与调参计划

- 设备：marble（Redmi Note 12 Turbo，`3e6f1443`），内核 `5.10.149-android12-9-00001-gda3d81545d1d-ab9545656`
- 分支：`main-510-port`
- 日期：2026-10-14
- 级别：M（只改 profile 时序参数，不动攻击代码）；§4 的取证载荷改动为 S/M

## 1. 问题定位

uid=0 已经稳定达成（v4b 21/30 命中、v4c 11/14 命中），P0-1（fork-hold）与 P0-2（W3 关闭）让**命中轮**不再重启。剩下的唯一瓶颈是**单次 pselect 的生还率**：

| 口径 | 观测 | 来源 |
| --- | --- | --- |
| 同 boot 连跑（SELinux 已 permissive ⇒ 每轮 1 次 pselect） | 24/24（v4b）、8/8（v4c） | `rounds-p01p02-v4b`、`rounds-p01p02-v4c` |
| 新 boot 首轮（需要 W1+W2 两次 pselect） | 3/6（v4c）、24/30 轮含 W1（v4b） | 同上 |

打偏的形态：内核 `pselect` 永不返回。日志止于

```
[*] consumer gate: waiter parked in syscall 72
```

之后没有任何输出；设备侧无 oops / panic / pstore 记录（kmsg 记录器在打偏时写不出盘，冻结时连存储路径都不可读）。

后果分两种：

- **新 boot 打偏**：`panic_on_oops=1` ⇒ panic ⇒ CPU 全停 ⇒ 硬件看门狗约 45 s 后复位（harness 判 `PANIC`）。
- **命中后打偏**：`panic_on_oops=0` 且 `gh-watchdog` 已 unbind ⇒ 内核卡死（harness 判 `FREEZE`）。2026-10-14 14:44 实测：`adb get-state` 仍答 `device`，但 `adb shell` 与 `adb pull` 全部超时 —— 连存储路径都被卡住。

因此两个仍未达成的目标其实是同一个数字：

- 目标①「每一轮都不重启」：生还率 85% ⇒ 每约 7 轮必有一次打偏。
- 目标② W3 + KernelSU：需要 13 次连续 pselect（`0.85^13 ≈ 12%`）。

## 2. 路线取舍

| 路线 | 说明 | 成本 | 结论 |
| --- | --- | --- | --- |
| A. 让打偏非致命（safe miss） | 改攻击代码，使丢失竞争时不 oops / 不死锁，让 `w1_attempts=15` 的重试真正生效 | L（攻击关键路径，需先有 oops 现场） | 方向正确，但**当前无证据**：冻结时拿不到内核现场，无法判断是哪个字段出错 |
| B. 提高单次生还率（调参） | 只改 profile 时序参数 | M，可快速迭代 | **本轮执行**：唯一不需要新证据的杠杆 |
| C. 收 oops 现场（流式记录器） | 取证载荷把 `/dev/kmsg` 通过**已建立的 socket** 流给主机（冻结时不需要 fork / 写盘） | S~M，只动取证载荷 | 与 B 并行准备：下次冻结就能拿到现场，为 A 铺路 |

## 3. 路线 B：参数扫描

### 3.1 使能：不需要重编 APK 的 profile 覆盖

App 把稀疏覆盖存在 SharedPreferences 文件 `ghostlock_prefs` 的键 `debug_profile_overrides` 里，值是 HOCON（release → 覆盖树）：

- `app/src/main/kotlin/com/ghostlock/app/data/AndroidProfileConfigController.kt:800-814`：`readDebugOverrides()` / `writeAdvancedOverride()`
- `app/src/main/kotlin/com/ghostlock/app/data/AndroidProfileConfigController.kt:890`：`const val PrefDebugProfileOverrides = "debug_profile_overrides"`
- `app/src/main/kotlin/com/ghostlock/app/data/AndroidGhostlockRepository.kt:75`：`getSharedPreferences("ghostlock_prefs", Context.MODE_PRIVATE)`

设备侧文件为 `/data/data/com.ghostlock.app/shared_prefs/ghostlock_prefs.xml`，可用 `run-as com.ghostlock.app` 读改写（保留其它键），重启 App 进程后生效。

**生效验证**：每轮 run 都会把本次生效配置写到 `Download/ghostlock-debug-log/<时间>/profile.conf`（同目录另有 `profile.bin`）⇒ 逐轮核对参数确实进了 native。

待实测项：覆盖层是否无条件生效（键名含 debug，可能受开关控制）；App 是否需要 force-stop 才重读。

### 3.2 测量口径

- 基线：40 轮、`-RebootEveryHits 40`（同 boot 连跑、不主动重启）⇒ 约 36 个单次 pselect 样本。
- 每个候选配置：同口径 30~40 轮。
- 主判据：同 boot 段的生还率；次判据：总命中率、`PANIC` / `FREEZE` 计数。
- 每组结束归档门禁记录（格式见 `docs/analysis/device-gates/`）。

### 3.3 候选参数（一次只动一个）

| 优先级 | 参数 | 当前值 | 机制假设 |
| --- | --- | --- | --- |
| 1 | `execution.routes.select_stack.enter_delay_us` | 50000 | consumer 进入 pselect 相对 owner 抢锁的窗口；窗口不匹配 ⇒ 抢锁失败 |
| 2 | `execution.race.setup_settle_us` | 50000 | 两次尝试之间的沉降；太短 ⇒ 上一次的 PI 链残留 |
| 3 | `execution.routes.select_stack.timeout_us` | 200000 | pselect 超时；对「永不返回」无效，但决定 attempt 节奏 |
| 4 | `execution.race.state_poll_interval_us` / `execution.routes.select_stack.consumer_burst_calls` | 1000 / 1 | consumer 轮询粒度与调用次数 |
| 5 | CPU 对（main=4 / consumer=5） | 固定 | 大小核与同簇竞争影响调度时序 |

## 4. 路线 C：收 oops 现场（并行准备）

### 4.1 C-lite：主机侧内核日志抓取（已实现，设备侧零改动）

`logcat -b kernel` 由 **adbd** 通过主机自己的 transport 泵出，不经过被卡死的 f2fs 路径，因此在 `FREEZE` 状态下仍可能把最后几行内核日志送到主机。

- 实现：`tools/trials/trials_ps4.ps1` 在轮次循环之前 `Start-Process adb -s <dev> logcat -b kernel -v time`，输出重定向到 `build/510profile/<tag>/kernel.log`，循环结束后 kill。
- 依据：2026-10-14 14:44 实测冻结设备 `adb get-state` 仍答 `device`，而 `adb shell` 与 `adb pull` 全部超时 ⇒ adbd 本身还活着，值得赌这条通道。

### 4.2 C-full：流式记录器（尚未实现）

现状：`dump_kmsg_head()` 与 `dump_pstore_snapshot()` 都写 `/data/local/tmp/glkfx/`（f2fs），冻结时不可读（已实测）。

改法：在 `src/core/session/victim_process.cpp` 的取证载荷里增加一路「已建立连接」的流式输出（启动时连接 `127.0.0.1:<port>`，harness 侧用 `adb forward` 接收）。冻结时主机仍能收到卡死前的内核日志，从而拿到路线 A 需要的现场。

只动取证载荷（命中后才执行），不影响 W1/W2 落地；按 S/M 级处理，需与门禁一起验证。

## 5. 风险

- 打偏仍会重启 / 冻机：每批次可能损失数分钟（harness 已有 `PANIC` / `FREEZE` 恢复路径）。
- 调参可能反向：v3 的 `SKB_RECLAIM_SENDS 4→16` 就是反例（9 轮零 W1 落地，见 `docs/analysis/5.10-payload-coverage-fix.md`）。
- 同 boot 连跑会累积状态（root worker 进程、SELinux permissive）⇒ 每组之间用主动重启清场，保证口径一致。

## 6. 判据与后续

- 成功判据：某配置把同 boot 生还率从约 85% 提到 ≥98%（30 轮内 0 次打偏），且不影响 W2 落地。
- 成功后立即进入 W3 重开实验：`w3_attempts=1`、`w3_chain_rounds=1`（1 次 leaf 探针 + 2 次写 = 3 次 pselect），目标是把 KernelSU 模块加载打通。
