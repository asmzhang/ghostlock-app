# marble 5.10「打偏即死」修复 v4：回收顺序（prepare cohort 提前释放）

状态：已实现，待真机验证（2026-10-14）
前置：`docs/analysis/5.10-payload-coverage-fix.md`（根因：内核在 `fake_lock` 处读到的页内容不是我们的填充）

## 1. 动机（为什么 v3「多盖章」不够）

v3（`SKB_RECLAIM_SENDS` 4→16、`RECLAIM_SOCKET_PAIRS` 1→8 ⇒ 每轮发送 128 次 = 8 MiB = 256 个
order-3 块，日志实测 `pairs=8 sends=128 bytes=8388608 errno=0`）在真机上 9 轮零 W1 落地
（同日基线 5/16 = 31%）。结论：**盖章次数不是瓶颈**——瓶颈是「泄漏页在开火那一刻是否在 buddy
空闲链表里，能被我们的 skb 拿走」。

`base = leaked & ~(ORDER3_SIZE-1)`（`src/core/support/util.cpp`）把泄漏 mm_struct 所在的
order-3 slab 页当作载荷页；只有当**整页 34 个 mm_struct 对象全部释放**时，该页才回到 buddy，
我们的 skb 才可能拿到它。因此真正要控制的是：**在发送前的一瞬间，谁的页是整页空闲的**。

## 2. 现状代码的顺序（`src/core/support/util.cpp`，`prepare_kernel_page`）

```
:720-727  关闭 pre_ctx (33) / post_ctx (33) 的 memfd      ← 释放早，发送前 ~700-900ms
:728-731  每 mm_objs_per_slab 关 1 个 spray memfd (6)
:733-738  关 pcp_shaping 对 + 4×sched_yield
:742-746  关 leak memfd（泄漏页所在 spray 组的最后一个引用）
:747-753  回收发送循环（SKB_RECLAIM_SENDS 次）
:757-761  关闭 prepare_ctx (272 = 8*mm_objs_per_slab) 的 memfd 并 kill 其子进程   ← 太晚
```

`prepare_ctx` 的 272 个对象恰好等于 **8 个整 page（8 × 34）**，这是代码里刻意的整页口径
（`heap_context.cpp` 里按 `mm_objs_per_slab` 对齐；`mm_objs_per_slab = ORDER3_SIZE /
profile.mm_struct_stride(MM_STRUCT_SZ)`，marble profile 的 `mm_struct_sz = 960` ⇒ 32768/960 = 34，
见 `app/src/main/assets/kernel_profiles/5.10.149-*.conf` 里引用的 `/proc/slabinfo`
`mm_struct 612 612 960 34 8`）。但它的释放发生在**发送之后**，对本次
回收毫无贡献。而提前释放的 pre/post（66 个 ≈ 2 页）+ spray 组（6 页）在泄漏识别与
等待期间（`+708~899ms`）有充足时间被系统的其它 mm 分配重新污染 ⇒ 发送时可用池远小于账面。

## 3. 改动（v4）

把 `:757-761` 的 prepare cohort 释放**上移到发送循环之前**（紧接 leak memfd 关闭之后），
即：先把 8 个整页还给 buddy，再立刻发送占页。

```cpp
        session::g_exploit_session.heap.leak_memfd.reset();
        /* v4: 先把 prepare cohort 的整页还给 buddy，再发送占页。 */
        for (size_t i = 0; i < prepare_ctx.childs.size(); i++) {
            SYSCHK(close(prepare_ctx.memfds[i]));
            prepare_ctx.memfds[i] = -1;
            kill_child(prepare_ctx.childs[i]);
        }
        for (int32_t i = 0; i < kernel::SKB_RECLAIM_SENDS; i++) { ... }
```

预期：发送瞬间 buddy 里属于我们的整页从 ~8 页提升到 ~16 页（pre/post 2 + spray 6 + prepare 8），
泄漏页命中「我们刚释放的页」的概率随之上升；若泄漏页恰好在 prepare cohort 的 8 页内，则
命中是必然的。

## 4. 判据

- 主判据：真机批次 W1 落地率（同口径 `W1=ok` 计）相对同日基线 5/16 = 31% 是否上升；
- 副判据：`[spray] payload ready ... +Nms` 的 N 不应显著变化（顺序改动不引入等待）；
- 安全判据：打偏轮的 `mb` 行为不劣化（不出现新的卡死形态）。

## 5. 风险与回退

- 风险：prepare 子进程提前死亡会改变 mm_struct 的**地址分布**（泄漏页可能变成 cohort 内页，
  与泄漏识别所依赖的 spray 页不同）；若落地率反而下降，说明泄漏页必须来自 spray 组 ⇒ 应改为
  「发送前逐个释放 spray 组并立即发送」（备选 A）。
- 回退：单文件一处顺序调整（8 行循环整体搬家），`git checkout -- src/core/support/util.cpp` 即回退到基线语义。
- 验证链：NDK 构建零告警 + `build/audit_shift.py` 语义审计（基线 `build/native/ghostlock.baseline-3542b61`）
  + `tools/cmp_disasm.py` 反汇编复核（见 §7）+ lint-tidy + 真机批次（KERNEL-PANIC-01：同构建复现 + 冷机复跑）。

## 6. 与 v3 的关系

v3 的两个常量（`SKB_RECLAIM_SENDS=16`、`RECLAIM_SOCKET_PAIRS=8`）已回退到基线值（4 / 1），
本轮构建与基线 APK 逐字节相同（包内 `libghostlock.so` sha256
`A2B8BF9DF34A21D57EA6DCFBD11640906A4B651FCB3B3A321446D4D1CC9B33AE`），作为 v4 的对照起点。

## 7. 反汇编复核（触及 prepare/reclaim 顺序，必须留证）

`tools/cmp_disasm.py` 新增目标 `prepare_good_kernel_page`：`prepare_kernel_page` 在 release
构建里被内联进该调用者（两个二进制的符号表里都没有独立符号），v4 改动的机器码只能在这里比对。

结果（基线 `build/native/ghostlock.baseline-3542b61`，候选 `build/native/ghostlock`）：

```
LAYOUT-SHIFT owner_thread: 69 instructions, 1 annotated address operands differ
LAYOUT-SHIFT waiter_thread: 917 instructions, 19 annotated address operands differ
LAYOUT-SHIFT consumer_thread: 367 instructions, 11 annotated address operands differ
LAYOUT-SHIFT run_main_route_threads: 414 instructions, 32 annotated address operands differ
LAYOUT-SHIFT do_kernel5_fake_lock_route: 173 instructions, 13 annotated address operands differ
LAYOUT-SHIFT do_one_write: 126 instructions, 3 annotated address operands differ
DIFF prepare_good_kernel_page: instruction count base=1987 cur=1996
SKIP multicast_owner_worker: absent from both binaries
SKIP multicast_waiter_worker: absent from both binaries
RESULT: FAIL
```

解读：其余 6 个攻击函数只有地址操作数差异（无形状变化）；两个 multicast worker 在两个二进制里
都不存在，属「无从比较」而非回归，工具已按 `SKIP` 处理并不再计入 FAIL（改动见
`tools/cmp_disasm.py`）。唯一的 FAIL 就是本次**有意**改动的 `prepare_good_kernel_page`：+9 条指令。

+9 条是真实形状变化：`build/tmp/disasm_diff.py` 的助记符级对齐显示编译器因新增循环重做了寄存器
分配与调度（相似度 0.951、53 个差异块），逐行自动对齐无法单独证明「只插入了目标循环」。因此补做
一次**受控对比**：把 `src/core/support/util.cpp` 单独回退到 HEAD（`git checkout --`）编出
`build/native/ghostlock.v4off`（md5 `0119484B7FA8F9C2CFCE81F57FDE1B64`），再恢复 v4 源码编出
`build/native/ghostlock`（md5 `DFB94C4322CBEDC423049444C0CC260C`）。两个二进制只差 v4 这一处改动：

```
IDENTICAL owner_thread (69 instructions, strict)
IDENTICAL waiter_thread (917 instructions, strict)
IDENTICAL consumer_thread (367 instructions, strict)
IDENTICAL run_main_route_threads (414 instructions, strict)
IDENTICAL do_kernel5_fake_lock_route (173 instructions, strict)
IDENTICAL do_one_write (126 instructions, strict)
DIFF prepare_good_kernel_page: instruction count base=1987 cur=1996
SKIP multicast_owner_worker: absent from both binaries
SKIP multicast_waiter_worker: absent from both binaries
RESULT: FAIL
```

其余 6 个攻击函数在受控对比下**逐字节相同（strict）**；`prepare_good_kernel_page` 的调用序列
（`llvm-objdump -d --disassemble-symbols=_ZN9ghostlock7support24prepare_good_kernel_pageERKNS_6memory12WriteRequestE`
提取 `bl` 目标序列）显示 v4 相对 v4off 只多出一次 `__errno@plt`（`kill_child()` 内联的 errno 访问），
且 **close + kill 这一对释放调用从 sendmsg 组之后移到了之前**（编号 = 该函数内 `bl` 序号）：

```
v4off: … 111:close 113:close 114:sendmsg 115:sendmsg 116:sendmsg 117:sendmsg 121:close 122:kill
v4   : … 111:close 113:close 114:close 115:kill 118:sendmsg 119:sendmsg 120:sendmsg 121:sendmsg
```

⇒ 机器码层面可确认：该函数的差异就是「prepare cohort 释放（`close` + `kill_child`）发生在发送
之前」，与源码 hunk 逐字对应，没有其它逻辑进入该函数。**注意**：v4 是**有意改变**回收顺序
（这正是本次改动的目的），不适用「顺序保持不变」的重构门禁；这里保留的是「除目标顺序外无其它
变化」的证据。复核仍以源码级 + 真机级两级证据收口：

- 源码级：`git diff -U4 -- src/core/support/util.cpp` 只有一处改动——既有的 prepare-cohort
  释放循环（8 行，循环体逐字未改）从发送循环**之后**整体搬到**之前**，没有新增或删除其它逻辑。
- 真机级：`docs/analysis/device-gates/2026-10-14-marble-v4-reclaim-order.md`（同口径批次统计）。
- 复现提示：受控对比必须**强制重编** `util.o`（`Remove-Item build/native/core/support/util.o`）。
  PowerShell `Copy-Item` 保留源文件 mtime，`git checkout --` 后直接拷回会让 make 认为 `util.o`
  仍是最新，从而链出旧对象——本次曾因此得到「v4 与 v4off 完全相同」的假结论（对比的其实是同一
  个二进制）。判断依据：先看两个文件的 md5 是否真的不同，再跑 `cmp_disasm.py`。
