## 2. 结论

1. **fd_set 拷贝是成功的**：内核确实用了我们写进受害者栈上的 `lock` 指针（fake_lock，与日志里的 `page=` 完全一致）。因此「consumer 开火早于 fd_set 拷贝」这一旧假设**排除**。
2. **载荷页内容不是我们的**：我们填充的假锁页布局是
   - `LOCK_OFF+0x00 = 0`（wait_lock）
   - `LOCK_OFF+0x08 = fake_w0`（waiters.rb_root.rb_node）
   - `LOCK_OFF+0x10 = fake_w0`（waiters.rb_leftmost）
   - `LOCK_OFF+0x18 = fake_task | 1`（owner）
   - `W0_OFF+0x00 = 1`（tree_entry.rb_parent_color = 黑根）、`+0x08 = 0`、`+0x10 = 0`

   以这份内容做 `rt_mutex_enqueue()`：`parent = *root = fake_w0`，随后读 `parent->rb_right`（= 0）即终止，`rb_link_node` 之后 `rb_insert_color` 看到 `parent->__rb_parent_color == 1`（黑）立刻 break ⇒ **不可能走到 `gparent` 解引用**。
   oops 里 `x9 = 0xffffff80378baf20`（直接映射区的地址，不是我们写入的任何值）且 `*(x9) = 0` ⇒ 树的第一个节点来自**其它内核对象/空闲 slab 的残留内容**（slab freelist 指针形状）⇒ **载荷页在泄漏地址处的内容不是我们的填充**。
3. **所以「打偏」不是时序问题，是分配器覆盖问题**：`base = leaked & ~(ORDER3_SIZE-1)`（`src/core/support/util.cpp:684`）假定「泄漏出的 mm_struct slab 页」就是我们 reclaim skb 占据的那一页；**这个假设只有约 20% 概率成立**（= 观测到的 W1 落点率 ≈ 20%）。
4. **写其实每次都发生**：`rt_mutex_adjust_prio_chain()` 先 `rt_mutex_dequeue()`（:663，写原语在这里发射）再 `rt_mutex_enqueue()`（:684）。命中轮与打偏轮都会执行到删除；只有「页是我们自己的」时才安全走完重插入 ⇒ 命中轮 uid 0 到手，打偏轮在重插入时崩在持 `pi_lock` 的原子上下文 ⇒ 狗在就重启、狗被 unbind 就整机冻结。

## 3. 修复方向（覆盖率）

`src/core/support/util.cpp:747-753` 目前只在一个 socketpair 上发 `SKB_RECLAIM_SENDS = 4`（`src/core/kernel/constants.hpp:23`）次、每次 `SKB_SEND_SIZE = ORDER3_SIZE*2 = 64 KiB`，且 `SO_SNDBUF` 被 `net.core.wmem_max` 削到约 208 KiB ⇒ 实际最多 3 次发送 ≈ 6 个 order-3 slab 的载荷页。被释放的 mm_struct slab 数量远大于此（`pre_ctx` 全部 + `post_ctx` 除最后一个 + `spray_ctx` 每 slab 一个）⇒ 覆盖率低 = 命中率低，且未覆盖时必然走野指针重插入。

修复：**把载荷页覆盖数量提高到远超被释放 slab 数量**。
- 用多组 socketpair（每组约 3 次 64 KiB 发送；组数建议 8，即 +16 个 fd）；
- 每组都是 `AF_UNIX/SOCK_STREAM` + `SO_SNDBUF/SO_RCVBUF = 1 MiB` + 非阻塞，发送同一份 `skb_buf()`（`SKB_SEND_SIZE` 字节，载荷结构在每个 32 KiB 块首 4 KiB 内，任意 32 KiB 对齐页都能自带完整结构）；
- 由于 fork-hold holder（`src/core/main.cpp:129` → `support::hold_reclaim_sockets_until_exit()`）是主进程 fork 出来的，**它会自动继承所有仍打开的 socket**，页在进程退出后依旧被钉住（P0-1 语义不变）；但需把这些 fd 纳入会话状态，才能被 `close_reclaim_sockets()/quarantine_reclaim_sockets()/has_reclaim()` 正确管理。

设计要求（AGENTS.md L 级）：
- `src/core/memory/heap_context.h`：`ReclaimPair reclaim;` → `std::array<ReclaimPair, kReclaimSocketPairs> reclaim;`；`has_reclaim()` = 任一对有效；move/close 遍历全部。
- `src/core/session/heap_context.cpp`：初始化/关闭/`has_reclaim()` 相应改写。
- `src/core/support/util.cpp`：`:18` 的 `reclaim_sv` 引用改为数组（第 0 对为主）；
  `:694-701` 建立全部 socketpair（第一个保持现有语义）；
  `:747-753` 对每一对做发送循环（`SKB_RECLAIM_SENDS` 次或 EAGAIN 即停）；
  `:269-347`（close/quarantine/hold）遍历全部对。
- `src/core/tests/heap_context_test.cpp`：同步为数组形态。
- fd 数量敏感：新增 fd 会占位，必须实测 fd 布局未被破坏（route setup 的 in0/in3/out0 与 `reserved 317 low fds` 日志不变）。

## 3.5 覆盖率定量（真机 /proc/slabinfo 实测，2026-10-14）

```
mm_struct  1112  1292  960  34  8 : tunables 0 0 0 : slabdata 38 38 0
```
- `objsize = 960 B`、`objperslab = 34`、`pagesperslab = 8` ⇒ **mm_struct 用 order-3（32 KiB）slab**，与 `ORDER3_SIZE` 假设一致。
- `slabdata 38 38`：全机 mm_struct 只有 38 个 slab（1.2 MiB）。
- 代码侧 `MM_STRUCT_SZ = 0x500`（1280，偏大）⇒ `mm_objs_per_slab = ORDER3_SIZE/MM_STRUCT_SZ = 25`（`src/core/support/util.cpp:548`）；攻击自身的人口：spray `(1+MM_PARTIALS)*25 = 150`、pre 24、post 25 ≈ 200 个 mm_struct ≈ 6 个 slab。
- reclaim 侧：`SKB_RECLAIM_SENDS = 4` 被 `net.core.wmem_max` 把 `SO_SNDBUF` 削到约 208 KiB ⇒ 实际约 3 次发送；AF_UNIX 的 frag cache 以 order-3 块（`skb_page_frag_refill`）取页 ⇒ 每次发送 64 KiB = **2 个 order-3 块** ⇒ 今天总共只消耗约 6 个 order-3 块。
- 只有「取到刚释放的那几个 slab」时才成立；buddy 的 order-3 空闲链上还排着大量其它块 ⇒ 命中约 1/5 ≈ 观测到的 20%。
- 修复后：8 组 socket × 约 3 次发送 ≈ 24 次 = **约 48 个 order-3 块**，足以把刚释放的 slab 全部吃下来 ⇒ 期望覆盖率接近 1。

## 5. 备选与风险

- 备选 A：不改 socket 数量，改为「泄漏-释放-发送」交错（每释放一个 slab 立刻发一页），覆盖率同样提升但需要把 `pre_ctx/post_ctx/spray_ctx` 的释放顺序与发送顺序对齐，改动面更大。
- 备选 B：用 `SO_SNDBUFFORCE` 突破 wmem_max（需要 CAP_NET_ADMIN，W1 阶段拿不到，不可行）。
- 备选 C（若覆盖率仍不足）：`src/core/support/util.cpp:713` 的 pcp shaping 只发 1 次；当 reclaim 发送次数提高后，用「每个 pair 各发一次 shaping」把本地陈旧 order-3 块提前吃掉，保证新释放的 slab 位于 buddy 空闲链头部。
- 风险：新增 fd 改变 fd 编号布局；新增发送改变 pcp/slab 局部性，可能反而降低命中率；两项都必须用真机批次判定（KERNEL-PANIC-01：同构建复现 + 冷机复跑）。

## 6. 对抗性复核结论（2026-10-14，独立复核，未参与实现）

复核者用 `D:\work\1\_ghostlock_refs\gki510-arm64\kernel-5.10` 原始 `Image` 反汇编 + System.map 重定位，逐条证伪第 1/2 节的判断。

**根因成立**（`rb_insert_color+0x48` 的 `f940050a ldr x10,[x8,#8]` 在镜像里字节一致；故障 VA = 8 ⇒ `x8 == 0`），但有两条必须写进记录的修正：

1. **崩的那次入队是「重入队」**：`x0 = 0xffffffc02edf3c30` 是内核栈上那个**真实** `rt_mutex_waiter`（不是我们页里 `fake_w0` 的合成副本）；它的 `__rb_parent_color = fake_lock|1`、`lock` 字段 = `fake_lock`，与种进栈槽的字（`src/core/route/waiter_words.cpp:53-64`，word 9 落 `+0x48`）一致 ⇒ **栈槽种植成功**，崩在 `rt_mutex_adjust_prio_chain` 走 requeue 分支时的**重入队**（`rtmutex.c:660-685`：先 `rt_mutex_dequeue` 再 `rt_mutex_enqueue`），不是第一次入队。
2. **日志里的 `fake_lock` 不能当作载荷页基址**：`src/core/kernel/target_constants.hpp:26-27` 是 `kLockOffset = 0x0e80`，当前二进制确实在 `[x8,#0xe80]` 存 `wzr`、`[x8,#0xe88]/[x8,#0xe90]` 存 w0 指针、`[x8,#0xe98]` 存 `fake_task|1`；而 round-7 日志是 `fake_lock == page == 0xffffff88cc238000`、`fake_w0 = page+0x300`。两者是构建/偏移漂移，现有物证无法判定 ⇒ 文档不要写死「lock 在页首」。

**「我们自己的填充不可能造成这次崩溃」（决定性）**：按 `src/core/support/util.cpp:431-433` 的填充，`LOCK_OFF+0x08`（`rb_root.rb_node`）与 `+0x10`（`rb_leftmost`）都写 `fake_w0`，而 `fake_w0` 处合成节点的 `__rb_parent_color = 1`（黑、父空）、左右孩子 = 0 ⇒ 插入攀爬第一步读到 1，`tbnz w8,#0` 命中，直接走结尾返回，**永远到不了 `+0x48` 的 `ldr x10,[x8,#8]`**。反过来：现场要求 `*(fake_lock+0x08)` 是一个**非我们写入的**内核地址（`0xffffff80378baf20`，其首 8 字节 = 0），而内核自己只可能写 `rb_leftmost`，或「root == 被擦节点」的自指情形 ⇒ 那个字从未被我们的填充写过。

**已排除的替代解释**：打偏早于 fd_set 拷贝（陈旧栈字仍指向我方页，其节点 pc=1 ⇒ 早退；且 `x1` 不会等于本轮 `fake_lock+8`）；页是我们的但被上一轮内核写坏；`rb_erase_cached` 破坏树；lock 指针不是我们的；整页全零（全零会走 `cbz` 早退）；崩在第一次入队（首次插入 `tree_pc = 1` ⇒ `tbnz` 命中 ⇒ 返回）。

**仍然存活的分叉（决定修法是否对症）**：无法区分「从未被盖章」（stomp 落到别的页/别的偏移，泄漏页从来不是我们的）与「盖过章但读之前被内核复用」。两者都是「页内容不是我们的填充」，但**前者靠提高覆盖率能修，后者不能** ⇒ 这正是真机批次要回答的问题；判据里的 `[spray] ... sends=/errno=` 用来确认我们的发送成功了几次（失败的发送既没盖章、也没把页钉住）。

## 后续验证结论（2026-10-14 补记）

本文提出的修复方向「把载荷页覆盖数量提高到远超被释放 slab 数量」已作为 **v3** 实测
（`SKB_RECLAIM_SENDS` 4→16、`RECLAIM_SOCKET_PAIRS` 1→8）：真机 9 轮 **零 W1 落地**
（基线同期 5/16 = 31%），故常量已回退到基线（4/1，对照构建包内 `libghostlock.so`
sha256 = `A2B8BF9D…` 与基线逐字节相同）。

实际有效的方向是**回收顺序**（v4：在发送前释放 prepare cohort，让 buddy 里属于我们的
整页从 ~8 页提升到 ~16 页），见 `docs/analysis/5.10-reclaim-order-v4.md`。
本文对「打偏」的机理分析（载荷页内容不是我们的、`rt_mutex_adjust_prio_chain` 重入队时
野指针）仍然成立，只是修复手段从「多盖章」改成了「让泄漏页更可能落在我们刚释放的页上」。
