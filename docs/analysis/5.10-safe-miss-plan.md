# 5.10 打偏硬化计划（safe miss）

级别：M（计划文档）；真正落地的代码改动属攻击关键路径（L 级），需 cmp_disasm 8 函数对比 + 真机门禁记录。

## 1. 问题与已确认事实

攻击链每轮需要 1–2 次 pselect（W1 + W2；同 boot 续跑时 W1 被 `attack::check_selinux_off()` 短路，只需 1 次）。
生还率按 2026-10-14 的 58 轮逐轮重放、按阶段标记重新分类（**同时纠正本文件早先把 `W1=ok`/`W2=entered`
当成生还计数的错误口径**——这两个字段是单轮内的阶段标记，不是生还数）：

| 分组 | 含义 | 轮数 | 命中 |
| ---- | ---- | ---- | ---- |
| 新 boot 首轮 | W1 + W2 两次 pselect | 38 | 26 = 68% |
| 同 boot 续跑 | 只跑 W2 一次 pselect | 20 | 17 = 85% |
| 对照组（v4 之前 APK） | 同一 harness | 15 | 0 |

⇒ 单次 pselect 生还率 ≈ 85%，两次 pselect 的合成 0.79 × 0.87 ≈ 0.69 与实测 68% 吻合。
打偏（pselect 不返回）的后果分两种：

| 场景 | 内核状态 | harness 判定 | 恢复方式 |
| ---- | -------- | ------------ | -------- |
| 新 boot 打偏 | `panic_on_oops=1`（CONFIG_PANIC_ON_OOPS_VALUE=1）+ 看门狗 armed | PANIC | QC 看门狗 ~45s 复位 |
| 命中后打偏 | child 已写 `panic_on_oops=0` + `disable_watchdog_modules()` 已 unbind | 先 TIMEOUT（系统还活着，uptime 可读），**下一次 PI 操作后** FREEZE | 只能人工/脚本复位 |

关键实测：`rounds-p01p02-baseline` r7 打偏后设备仍可读 uptime（up_after=913.53），紧接着的 r8 才整机冻死
⇒ **一次打偏不会立刻杀死设备，是随后的 futex/PI 操作把它彻底锁死**。

### 1.1 日志级证据：失败全部停在第一次 pselect（2026-10-14 新增）

对 44 个轮次日志（v4b 30 + baseline 8 + enter150 6）逐轮计数 `pselect pre-select` /
`pselect post-select` / `consumer gate` 三组标记：

| 轮次结果 | pre | post | gate |
| -------- | --- | ---- | ---- |
| 命中（新 boot） | 2 | 2 | 2 |
| 命中（同 boot） | 1 | 1 | 1 |
| 打偏（PANIC / FREEZE / MISS / TIMEOUT） | 1 或 2 | pre − 1 | = pre |

所有打偏轮的日志尾部**逐字相同**，止于：

```
[*] pselect pre-select attempt=1/4 compact=2 +0ms
[*] consumer gate: waiter parked in syscall 72
```

`pselect post-select` 从不出现 ⇒ 线程**停在 syscall 内部没有返回**，而且停在 `attempt=1/4`。
采样五个（尾部逐字一致）：`rounds-p01p02-enter150/round-6.full.log`（MISS，设备存活）、
`rounds-p01p02-baseline/round-7.full.log`（TIMEOUT，设备存活）、`rounds-p01p02-v4b/round-2.full.log` 与
`rounds-p01p02-v4b/round-8.full.log`（PANIC）、`rounds-p01p02-v4b/round-21.full.log`（FREEZE）。

**推论（本计划的关键论据）**：`src/core/route/select_stack_route.cpp:434` 的 `attempts = 4`
（`compact_waiter = 2` ⇒ `value_or(0) != 0`）与 profile 的 `w1_attempts = 15` / `w2_attempts = 15`
在打偏时**全部不可达**——重试阶梯只在 pselect *返回* 之后才推进（`:506-516`：只有
`calls > 0 && successes > 0` 才置 `ROUTE_OK`，否则 `fail(33)` 后 `continue`），而打偏的定义就是"不返回"。
所以当前每轮实际只有 1 次 pselect 机会，**重试参数对命中率零贡献**。

⇒ 打偏硬化（§4 的 E1）不只是"让失败变软"：一旦打偏能返回，已有的 15×4 重试阶梯立刻生效，
每阶段失败率从 15% 量级降到 0.15^60 量级；W3 的 13 次 pselect 也随之从"不可行"变成"可行"。
这是同时服务"每轮不重启"与"重开 W3 / KernelSU"的唯一杠杆。

## 3. 机制（已由内核源码确认）

1. 触发路径不是 pselect，而是 **`sched_setattr`**：`__do_sys_sched_setattr` → `__sched_setscheduler`
   → `rt_mutex_adjust_pi(task)` → `rt_mutex_adjust_prio_chain`（`kernel/locking/rtmutex.c:1136-1143`）。
2. 崩溃调用点在 `rtmutex.c:713-745`（`[11] requeue the pi waiters`）：`:721-722` 或 `:736-738` 的
   `rt_mutex_enqueue_pi(task, waiter)` → `rtmutex.c:305-326`
   `rb_insert_color_cached(&waiter->pi_tree_entry, &task->pi_waiters, leftmost)`。
3. 该节点的 `__rb_parent_color` 由我们种入：`route/waiter_words.cpp:44`
   `relink_pc = right != 0 ? right : write_target - 8`，`:57` word5 = `pi_pc`；
   `right` 来自 `memory/payload_builder.cpp:65-69`（W1 value write ⇒ `page_base + 0x100`，
   W2 credential ⇒ `init_cred_alias`），leaf write 分支则用 `:74` `layout.parent = request->target - 8`。
4. 内核 rbtree 语义：`rb_is_black(parent)` 只读 `*(parent) & 1`。若为 0（"红"）则
   `gparent = *(parent)`，紧接着读 `gparent->rb_right`（`struct rb_node` 偏移 **0x8**）。
   **只有 `*(pi_pc) == 0` 才会正好崩在 0x8** —— 观测地址 0x8 ⇒ `*(pi_pc) == 0`。
   W1 的 `pi_pc = payload page + 0x100` 是我们自己页里的零字节 ⇒ 与观测完全吻合。
5. ⇒ 打偏 oops 是**数据相关**的：取决于 `*(pi_pc)` 那一个字，不是无条件发生。

**H1 已推翻，原"变体 A"禁止实施**：5.10 的 `pi_waiters` 是 `struct rb_root_cached`，不是 `plist_head`
（`rtmutex.c:307/324/333`、`include/linux/rtmutex_common.h:27-30`），空树本来就是 `{0,0}`。
把 `rb_root.rb_node` 写成非空伪指针会让 `task_has_pi_waiters()` 恒真 ⇒ 非法遍历，只会更糟。

## 4. 实验设计（替换原变体 A/B/C）

1. **E2（先做，机制确认，最小改动）**：把 `pi_pc` 指向的那个字（W1 = payload page + 0x100）
   写成 `0x1000`。若 oops 地址从 `0x8` 变成 `0x1008`，则"`*(pi_pc)` 决定 gparent"被直接证实。
2. **E1（硬化，目标）**：把该字写成**奇数**（bit0 = 1）⇒ `rb_is_black(parent)` 为真 ⇒
   `rb_insert_color` 走 `break` 干净退出，不再读 gparent。观察打偏轮 PANIC/FREEZE 是否消失；
   若命中率同时归零，说明这条 pc 也是写原语的一部分，该方向不可行，需改种 `tree_entry` 侧。
3. **静态确认（E1 之前必做）**：确认 W1/W2 的写到底落在 `tree_entry` 还是 `pi_tree_entry`，
   以及 `request->preserve_child` 走哪一支（决定 `relink_pc` 取 `right` 还是 `target-8`），
   否则 E1 会改错字段。
4. 每组 20–30 轮，与基线（v4b/v4c/baseline/enter150b）比较 `命中率 / PANIC / FREEZE / MISS` 四项。
5. 判定：打偏轮不再出现 PANIC 或 FREEZE 且命中率不低于基线 ⇒ 硬化成立；否则回退。
6. **强判定**（由 §1.1 推论得出）：若打偏变成"可返回的失败"，命中率**应当上升**（15×4 阶梯生效）。
   命中率 ≥ 99% 即强证据；若仍停在 ~73–85%，说明硬化未真正消除打偏路径。

## 7. 追加：崩溃节点身份与页重建（2026-10-14，修正 §3.4 / §4 的 E1）

§3.4 的逻辑仍然成立（**父节点的 `__rb_parent_color` 必须为 0**，且 `*link` 落在 `parent + 0x8`），
但"父节点就是我们种下的 `pi_pc`"这一步被下列证据推翻。

### 7.1 父节点是一个 payload 页基址

oops 寄存器（`build/510profile/frozen-1442/kmsg-tail.bin`，两份记录完全相同）：

| 寄存器 | 值 | 含义 |
| ------ | -- | ---- |
| x27 | `ffffff88bcf78000` | 父节点地址（**页对齐**） |
| x1  | `ffffff88bcf78008` | `*link` 存储地址 = `parent + 8` ⇒ 落点在 `parent->rb_right` |
| x6/x13 | `0x8` | 故障地址 = `gparent + 8`，`gparent = 0` |
| x5/x19 | `ffffff87db900000` | 另一个**页对齐**地址（与父节点不同页） |

`ffffff88bcf78000` 是页对齐地址，与 `select_stack_route` 自己的布局完全一致：
`pselect route setup ... page=ffffff887f3d0000 fake_lock=ffffff887f3d0000 fake_w0=...+0x300
fake_task=...+0x400`（`build/510profile/rounds-p01p02-v4b/round-1.full.log:67`）
⇒ **`fake_lock = page + 0x0000` 是页对齐的**，父节点就是某个 payload 页的 `fake_lock` 位置。
`*(page + 0)` = 0（页首 8 字节为零）⇒ `gparent = 0` ⇒ 崩在 `0x8`。

### 7.2 为什么"第一棵空树"不会崩、而这里会崩

- `src/core/support/util.cpp:509-518`：`fake_task` 的 `pi_waiters` 被种成**空树**
  （`:514` `put64(p, fake_task_off + ft_pi_wait_off, 0)`、`:515` `...+0x08` 亦为 0）。
  空树下 `while (*link)` 不执行 ⇒ `parent = NULL` ⇒ `rb_link_node(node, NULL, ...)` ⇒
  `rb_insert_color` 第一分支 `if (unlikely(!parent))` 直接 `break`，**安全**。
- ⇒ 崩溃要求树里**已经有节点**，且该节点所在内存的 8 字节头为零。
- `src/core/route/select_stack_route.cpp:429-447`：compact 路由 `attempts = 4`，**每次 attempt 都
  `prepare_good_kernel_page()` 重建 payload 页**（`:439-447`），上一轮 attempt 留在树里的节点
  仍指向**旧页**，旧页被释放/重写后头部归零 ⇒ 下一次 PI 走查命中该陈旧节点 ⇒ 崩在 `0x8`。
  这与 `:429-433` 的注释（"a lost race clobbers the page, so every attempt resprays"）是同一件事的两面。

### 7.3 为什么 select_stack 没有清理这一步

`src/core/race/threads.cpp:104-115` 的收尾（`FUTEX_LOCK_PI` + 已过期 timeout ⇒ 强制走慢路径
⇒ `remove_waiter()`）由 `route::route_needs_ghost_disarm()` 把关，而该函数
（`src/core/route/route_policy.hpp:271`）**只对 multicast policy 返回 true**；
`src/core/tests/route_policy_test.cpp:100-101` 明确断言 select/tcp 为 false。
⇒ 我们跑的 select_stack 路由**从不做 ghost disarm**，而 `threads.cpp:104-109` 的注释正是这个风险的记录
（"thread exit leaves a walkable dangling ghost and the next mm_struct spray can panic the kernel"）。

### 7.4 修正后的候选修复（替换 §4 的 E1）

1. **F1（首选，复用已验证代码）**：把 ghost disarm 从"路由结束后一次"改成"**每次 attempt 之后、
   重建 payload 页之前**"执行；同时让 select_stack 路由也走这一步（`route_needs_ghost_disarm`
   放开 select，或直接在 `select_stack_route.cpp:438` 的循环里调用 disarm）。
2. **F2（更保守）**：attempts>1 时**不释放旧 payload 页**（保留 4 页直到进程结束），
   使树里陈旧节点所在内存始终有效（头 8 字节不再是 0）。
3. **F3**：`attempts = 1`（取消同进程内重试）⇒ 消除"旧页节点"，但会丢掉 4 次重试阶梯，仅作对照。

### 7.5 先做的判别实验（E2′，比 §4 的 E2 更强）

把 payload 页偏移 0 与偏移 0x100 各写一个哨兵（例如 `0x1000` / `0x2000`），跑若干轮直到再次打偏：
- 若 oops 故障地址为 `0x1008` ⇒ 父节点 = `page + 0x000`（`fake_lock`，与 §7.1 一致）；
- 若为 `0x2008` ⇒ 父节点 = `page + 0x100`（即 §3.4 原判断的 `pi_pc`）。
这一步只需一个诊断构建，能一次性定死节点身份，避免 F1/F2 改错位置。

## 5. 风险与代价

- `pi_waiters` 参与 reinsertion，改动可能降低命中率 ⇒ 必须同时看命中率，不能只看打偏是否变软。
- 属攻击关键路径：需要 `tools/cmp_disasm.py` 8 函数对比 + 真机门禁归档。
- 每轮实验约 30 分钟（含命中后主动重启）。

## 6. 并行工作

- 参数扫描批次 `rounds-p01p02-enter150`（`enter_delay_us` 50000 → 150000，20 轮）用于先确认
  「时序参数是否是生还率的杠杆」；若显著，则先调参再谈硬化。

## 8. 已实施的修复：黑节点地毯（2026-10-15 落地并真机验证）

### 8.1 崩溃点的寄存器证据（修正 §7.1）
§7.1 把 `x27 = ffffff88bcf78000` 读成「父节点」。现场更支持另一种读法：故障虚拟地址是 `0x8`，
而 `x1 = x27 + 8` 是**有效**地址，所以被解引用的基址不是 x27 而是 0
（`rb_insert_color` 的 `gparent->rb_right`，`gparent = 0`）；x27 只是现场仍活着的 payload 页基址寄存器。

⇒ `rb_is_black(parent)` 为假 ⇒ `gparent = *(parent) = 0` ⇒ 这个 `parent` 就是**写值本身**
（`node->__rb_parent_color` = 写值；5.10 词表 `tree_pc`/`pi_pc` = 写值），而写值地址处的内容是 0：
W1 写值 `page_base + 0x100` 正是 pselect 的 in-set 缓冲（`waiter_shift = -2` 丢掉前两个 fd word
⇒ 该处头 16 字节全 0）。

### 8.2 修复内容
`rb_insert_color()` 只在 `*(parent) & 1` 为 0 时继续下降；把内核可能当成节点的字写成奇数，
下降就会在第一次读后立刻 break。落地三处：
1. `src/core/kernel/target_constants.hpp:31-35` 新增 `kRelinkNodeOffset = 0x0200`
   （`src/core/kernel/target.h:130-133` 映射为 `kernel::RELINK_NODE_OFF`）。
2. `src/core/support/util.cpp` compact 种植块（`LOCK_OFF + 0x18` 之后）写
   `put64(p, 0x00, 1)` 与 `RELINK_NODE_OFF + 0x00/0x08/0x10 = 1/0/0`（自洽黑节点：parent 0、无子节点）。
3. `src/core/memory/payload_builder.cpp:65-73` W1 写值 `page_base + 0x100` → `page_base + RELINK_NODE_OFF`；
   固定向量期望值 `0xffffff8800210100` → `0xffffff8800210200`。

写原语不变：写仍由 erase relink 完成，`*(value)` 只被 `rb_is_black` 读一次；W1 存入目标字段的字节
除 byte1（0x01 → 0x02，两者都非 0，布尔语义相同）外不变，byte0 = 0（`enforcing`）与 byte2
（`initialized`，来自 chunk 的 bit16）都不变，`payload_write_layout_accepts_page()` 的 bit16 判据不变。
W2 写值仍是 `init_cred_alias`（语义要求），本次未改。

### 8.3 验证与判定
- 构建：NDK 重建 0 警告，二进制 md5 `92965C4C055696846D5EAF04A7CFFDF8`（2782808 B，较前一版 +64 B）；
  WSL host tests 27/29 PASS（唯一失败是既有的 `tcp_zerocopy_route_test` 的 `yield` 汇编）。
- 真机批次 `rounds-p01p02-blacknode`（15 轮，`-RebootAfterHit`，每轮冷启动）。
- **强判定**：PANIC/FREEZE 归零 ⇒ 修复成立，`attempts=4` 重试阶梯才有意义（~73% → ~99%），
  W3 的 13 次 pselect 才可能可行。若 PANIC/FREEZE 仍在且故障地址仍是 `0x8` ⇒ 父节点不是写值
  （转 §7.4 的 F1/F2）；若故障地址变成 `0x1008`/`0x2008` ⇒ 父节点确实是写值但地毯没生效。
