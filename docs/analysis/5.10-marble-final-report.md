# marble 5.10：App 直跑取 root —— 实测结论与操作建议

设备 Redmi Note 12 Turbo（marble / SM7475），内核
`5.10.149-android12-9-00001-gda3d81545d1d-ab9545656`，Android 13 / MIUI V14.0.27.0.TMRCNXM。
分支 `main-510-port`（基线是上游 `origin/main` = `3d4306c`）。本文只记录**实测到的**结论，
不把未验证的猜测写成结论。

---

## 1. 达成了什么

App 内点一次「执行」→ native 跑 exploit → 子进程拿到 uid 0：

```
[*] pselect post-select attempt=1/4 compact=2 +201ms ret=4     ← W1（SELinux）
[*] pselect route done calls=1 success=1 status=0 clean=1/1
[+] SELinux permissive
[*] pselect post-select attempt=1/4 compact=2 +203ms ret=5     ← W2（child cred）
[*] pselect route done calls=1 success=1 status=0 clean=1/1
[*] child uid = 0
[+] child is root!
[*] fork-hold parked pid=21820; reclaim sockets survive this exit
```

* 全程只有手机，不需要 PC 侧任何东西。
* **命中那一轮设备不重启**：命中轮的 `up_after` 恒大于 `up_before`（40 轮里 27 次命中全部如此）。
* 命中率（冷启动、每轮一次联网尝试）：

| 指标 | 数值 |
|---|---|
| HIT-ROOT | **27 / 40 = 67.5%** |
| 失败（PANIC，干净重启） | 13 / 40 = 32.5% |
| 单次 pselect 生还（W1） | 30 / 40 = **75%** |
| 单次 pselect 生还（W2） | 27 / 30 = **90%** |

（两批冷启动批量：`build/510profile/rounds-w1rate2` 20 轮、`rounds-quarantine` 20 轮。
0.75 × 0.90 = 0.675，与实测 27/40 完全吻合。）

---

## 2. 失败长什么样

**一次 pselect 只有两种结局：要么返回并写成功，要么线程永远不返回。**

* 命中轮：`pselect route setup` 2 次、`pselect post-select` 2 次 —— 两次 syscall 都返回了。
* 失败轮：`setup` 1 次、`post-select` **0 次** —— 卡在 `pselect pre-select` + `consumer gate` 之后，
  内核里就再也没出来过。

失败轮的三种下场：

1. **冷启动**（`panic_on_oops=1`、`gh-watchdog` 已绑定）⇒ 内核 panic ⇒ **一次干净重启**，约 90 秒后
   可重试。这是 40 轮里 13 次失败的全部表现。
2. **同一 boot 内「已被命中轮解除武装」之后又跑一次**（命中轮的 root 子进程写过
   `panic_on_oops=0` 并 `unbind` 了 `gh-watchdog`）⇒ **永久卡死**：load 冲到 ~75、大量进程进 D 态、
   adb 能应答但整机跑不动，只能长按电源。实测发生过两次。
3. **极少数（1/41）机器不出事**，只是那一个线程挂住（`rounds-fsync` round 12）。

---

## 3. ★ 重试阶梯从来没跑起来过

`w1_attempts = 15`、`w2_attempts = 15`、compact 路由的 `attempts = 4` —— 这些数字**一个都没生效过**：

* 91 次 pselect 尝试里，`attempt=2/4` 出现 **0 次**；
* 因为「打偏」不是返回一个失败码，而是**线程不返回**。重试循环写在 syscall 之后，永远到不了。

所以真实可靠性 = 两次独立硬币（75% × 90%），而不是「15 次重试把 20% 拉到 95%」。
这一点决定了：**要彻底消灭重启，必须让打偏能返回**；在那之前，任何调 `attempts` 的工作都是白做。

## 4. 一路修好并已验证的东西

| 项 | 说明 | 判据 |
|---|---|---|
| 5.10 compact waiter | `compact_waiter = 2`（0/1/2 = 6.6 rb_node / 6.1 compact / 5.10 compact），零 schema 改动 | 真机 `compact=2` 生效 |
| marble profile | 偏移全部来自 ROM 内核（`tools/extract_rs` 对 `rom_kernel.bin` 推出 9 个符号，与 my2 表逐项一致） | `init_cred image=ffffffc0827a0930 alias=ffffff802a7a0930` |
| `reserve_low_fds` + `raise_pipe_fd` | fd_set 位图横跨 0..319，低 fd 会被 W2 的写值点亮 | `reserved 317 low fds` |
| perf 取任务 | ring 32→256 页、候选池 256→8192、三票多数 | `perf task: … (7780/8192 votes)` 三票一致 |
| Path A 门闩 | 消费者只在 `/proc/<tid>/syscall` 确认 waiter 已停在 `pselect6`(72) 后才开火 | `consumer gate: waiter parked in syscall 72` |
| 黑节点地毯 | W1 写值从 `page+0x100` 挪到 `page+0x200` 并在那里种自洽黑节点 | 真机 `in0=…0200` |
| P0-1 fork-hold | 命中后 park 一个 holder，reclaim socket 不随父进程退出而释放 | 命中轮 27/27 都有 `fork-hold parked` |
| kmsg 取证加固 | 采集器每次 write 后 fsync、`close_range` 收 fd、`oom_score_adj=-1000` | 已在真机跑 |
| W3 关闭 | `w3_attempts = 0`：W3 只服务 KernelSU late-load，与 uid 0 无关，却要多赌最多 13 次 pselect | `debug.execution.stages.w3_attempts=0` |

## 5. 最后一次改动：要诚实

`src/core/support/util.cpp` 的 `prepare_kernel_page()` 里，把「关闭上一张 payload 页」改成
「把它 quarantine 住」（理由：打偏留在 PI 树里的陈旧节点指向被释放的页，读回全 0 ⇒ 正好是
「红节点没有祖父」）。

**它没有可证实的收益。** 两批对比：

| | rounds-w1rate2 | rounds-quarantine |
|---|---|---|
| HIT-ROOT | 14/20 (70%) | 13/20 (65%) |
| W1 打偏 | 3/20 | 7/20 |
| W2 打偏 | 3/17 | 0/13 |

W2 从 3/17 变成 0/13 看起来像好了，但由 §3 可知：**重试阶梯从不运行，所以一次「被救回来的打偏」
在日志里必然表现为 `attempt=2/4`，而它一次都没出现过。** 因此 0/13 更可能是小样本噪声。
改动本身代价为零、机制上讲得通，所以保留，但**不当作已解决的证据**。

## 6. 今天怎么用（操作建议）

1. **每次尝试前先重启手机**（或确认是刚开机）。这样打偏只会换来一次约 90 秒的干净重启，
   永远不会卡死。
2. **成功拿到 root 之后，不要在同一 boot 里再点一次「执行」**；要再试就先重启。
   （卡死的两个案例都出在这里。）
3. 平均大约**点两次**能中一次（单次 67.5%）。
4. 万一真卡死了：长按电源键约 10 秒强制重启。adb 救不回来（`adb reboot` 也要等内核能动）。

## 7. 没解决的、以及如果继续做该从哪里下手

**唯一的根问题：打偏会让内核在 PI 流程里卡住，而我们种下去的东西挡不住它。**
在这个问题解决之前，「全程不重启」做不到。

* **证据缺口**：打偏那一轮内核一个字都没多打（141 MB 的 kmsg 尾巴里 0 条新记录），
  更像自旋/死锁而不是 oops；但本机 ramoops/pstore 从不注册，拿不到内核证词。
* **未试过的杠杆**：
  1. 让 select_stack 也做 ghost disarm（现在 `route_needs_ghost_disarm()` 只对 multicast 返回 true，
     `src/core/route/route_policy.hpp`）。它只能清理「路由之后」的悬挂节点，理论上救不了正在卡死的
     这一次，但能救「W1 成功后的 W2 走到陈旧节点」这一类 —— 而 W2 的 3 次打偏正是这一类。
  2. 把一次 run 的赌注从 2 次减到 1 次（跳过 W1）。代价是 SELinux 仍是 enforcing，
     拿到的 uid 0 在 SELinux 下能做的事有限，只适合「先只求 uid 0」这个验收口径。
* **已经排除的方向**：`enter_delay_us` 参数扫描没用 —— 门闩确认后这条延迟会被跳过，
  40 轮日志里 `gate=confirmed` 恒成立，所以那个参数根本不参与。
