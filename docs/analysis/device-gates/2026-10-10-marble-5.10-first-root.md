# Device gate: marble 5.10.149 — first root without reboot (path A)

## 结论

在 Redmi Note 12 Turbo（marble，`3e6f1443`，内核 `5.10.149-android12-9-00001-gda3d81545d1d-ab9545656`）上，
App 内直接跑通 exploit 并让 child 拿到 **uid 0**，且 **该轮设备没有重启**。

这是 select_stack 路由首次在 5.10 的 compact rt_mutex_waiter 布局上走完 W2。2026-10-12 起在
P0-1（fork-hold）+ P0-2（profile 关 W3）加固版上复现成功且同轮无重启（见下文 b 批次 round 1、
c 批次 round 16/20）。截至 c 批次，marble 上 uid=0 共命中 **5 轮**（pathA round 3/4、
b round 1、c round 16/20，其中 P0-1+P0-2 加固版 3 轮全部无重启）。

## 失败点已从 W2 移到 W3

同一轮在 `child is root!` 之后继续走到：

```
[*] W3-0: leaf dir attempt 1/4
[*] === W3-0: leaf dir === target=0xffffff880c0a1a10 mode=1 leaf=1
[*] [spray] mm spray + kernelsnitch ready (cpu=8) +95ms
```

round 3 的日志快照止于 W3-0 spray 起点（HIT verdict 一到就抓快照，native 还在继续跑）；设备没有死
—— **round 4 在同一 boot 内再次拿到 uid 0**（见下节）。**提权本身不依赖重启；真正崩的是之后的
W3（seccomp 清除）阶段。**

my2 的成功轮（`_ghostlock_refs/gl3_root_success.log`）在 `child is root!` 后打的是
`[+] no app seccomp filter (adb/shell flow); skipping W3` —— 因为它是从 adb shell 跑的
（`Seccomp=0`），fork 继承无过滤器，所以**根本不需要 W3**。App 内跑是 `Seccomp=2`，
必须清掉 child 的 `TIF_SECCOMP` + `seccomp.mode` 才能 exec 出可用的 root shell。

## round 4：同 boot 第二次 uid 0（补记 2026-10-12）

round 3 命中后设备未重启，harness 继续跑了 round 4：W1 因 SELinux 已 permissive 直接跳过
（`SELinux already permissive`，`cve_2026_43499_backend.cpp` 早退路径），W2 再次命中：

```
[*] === W2: cred === target=0xffffff880c0a1a00 mode=2 leaf=0
[*] consumer gate: waiter parked in syscall 72
[*] pselect post-select attempt=1/4 compact=2 +204ms ret=7
[*] pselect route done calls=1 success=1 status=0 clean=1/1 step=0 errno=0
[*] child uid = 0
[+] child is root!
GLK_STATUS w2a completed
GLK_STATUS w3a in_progress
[*] W3-0: leaf dir attempt 1/4
```

随后走完第二次 heap spray（`mm_struct leaked=0xffffff804e7e3840`、`prepare_kernel_page ok
attempt=1`）、waiter parked（`syscall 72`）之后日志终止——设备死于 **W3-0 第二次 pselect 内**。
这解释了原始记录的「round 4 期间重启」：不是 round 3 的余波，而是 round 4 自己在 W3 阶段 panic
（`CONFIG_PANIC_ON_OOPS=y`，见 handoff 文档）。证据：`build/510profile/rounds-pathA/round-4.full.log`
（该轮无 summary verdict 行，末轮死亡）。

## 2026-10-12 批次 rounds-p01p02-b round 1：P0-1 + P0-2 首证

P0-1 = fork-hold（`src/core/support/util.cpp:298 hold_reclaim_sockets_until_exit()`，调用点
`src/core/main.cpp:118`）：fork 子进程抑制 reclaim socket 释放路径（`unix_release_sock →
skb_release_data → put_page`），防 run 正常退出时 `BUG: Bad page state` 重启。
P0-2 = profile 关 W3（`w3_attempts 6→0`、`w3_chain_rounds 3→1`，backend `:276` 早退）。

## 未决

1. ~~W3 阶段（`child_task + task_comm_off` leaf dir 写、第二次 heap spray）为何崩溃。~~
   → 已由 P0-2 路线回答：不再攻击 W3，profile 直接 `w3_attempts=0` 关闭该阶段；代价是
     KernelSU 模块无法 late-load（ksud 被 app seccomp filter 阻断），只能拿到 temporary root。
2. 是否移植 my2 root 脚本里的 panic 抑制（`panic_on_oops=0` / `panic_on_rcu_stall=0`）——
   上游 `origin/main` 的 root 脚本没有这两行，于是每次 oops 都要付 ~70s 重启代价。
3. fork-hold holder 的 oom_score_adj 实测 0（代码应写 -1000，`util.cpp:338-342` 写后不查返回值）；
   hold 功能不受影响（靠 fd 存活），但值得查明写失败原因。
4. W3 被关后 root shell worker 继承 `Seccomp: 2 filters=1`，root 脚本在第一条写日志语句即死
   （zygote seccomp 阻断）——若要真正加载 KernelSU 模块，仍需回答「如何在 seccomp 下让 root
   脚本存活」（例如 W3 攻击本身，或从无过滤器上下文 spawn worker）。

## 补记（2026-10-14）

- 未决 2 已落地：panic 抑制改由**被提权 child 本身**在 handoff 前写（root 脚本路线不可行——worker
  继承 zygote seccomp filter，死于脚本首条语句），实现见 `src/core/session/victim_process.cpp` 的
  `suppress_panic_reboot()`；真机取证 `/data/local/tmp/glkfx/param-panic_on_oops` 实测 `0`
  （该设备 `CONFIG_PANIC_ON_OOPS=y`，默认应为 1）。
- 未决 1 的量化后续：W3 由 profile 关闭后，真正决定成败的是 **W1 落地率**；v4（prepare-cohort
  释放顺序）把同日基线的 4/15 = 26.7% 提升到 17/22 = 77.3%，见
  `docs/analysis/device-gates/2026-10-14-marble-v4-reclaim-order.md`。
- 未决 3 仍未查（需要一次不跑批次的窗口读 fork-hold holder 的 `/proc/<pid>/oom_score_adj`）。
